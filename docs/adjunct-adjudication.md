# 增味裁决与两次调用

玩家在砧板上写材料、处理方式、克数和投放阶段。填写发生在同一页，实际作用按记录的工艺时点重演。想比较“生蒜拍碎后随酵母投”与“烤熟后在分装前投”，两次使用同一锅基底、相同的种子即可。

## 从同一份原料推到成酒

| 来源 | 引擎结算的内容 | 例子 |
|---|---|---|
| 直接风味 | 原料本身可感知的香气、主味及其保留量 | 新鲜蒜辛、烤蒜甜香 |
| 成分转化 | 共享初始成分的可转化份额；温度、投放阶段和剩余发酵决定留存与变化 | 部分鲜蒜辛香转为较柔和的葱蒜气息 |
| 酵母响应 | 以 g/L 和投放时点将潜在促进或抑制折算为四档，再作用于发酵进程 | 低负荷维持原轨迹，高负荷可令规定时间内的发酵接近停滞 |

每项记录可以写具体分子或化学类别，并同时注明依据、把握程度、直接味和转化物。常见路径分为直接留存、热转化、酵母参与的转化和接触期间分解。全锅最多取三份代表性成分。这里的份额只分配游戏中的风味贡献，与化学质量分数无关。

同一份成分若转化为另一种味道，原有份额会相应减少。酵母响应还会间接改变残糖、酒精和酵母产生的风味。酒龄、包装状态和目标风格在品尝时读入。材料很陌生时，模型可以只报化学类别、低把握或空路径。离线无法辨认的材料保留名字和投放记录，缺少依据的影响取零。大蒜素对酵母和巯基反应的实验依据与游戏里的鲜蒜克数阈值要分开。配料重量没有到大蒜素浓度的通用换算。[酵母实验](https://pubmed.ncbi.nlm.nih.gov/20883774/)

## 成酒

`POST /api/adjudicate` 只交给服务端处理。给模型的是未增味基酒的指标和感官底稿、少量公开配方参照、材料及处理、体积、用量、菌株和工艺。一次 Responses 请求返回结构化画像和成酒品鉴、BJCP 评语的句式。画像经字段与取值验证后，游戏重跑同一锅，把最终杯色、香气、入口、收口和申报风格偏差填进文字。这样模型可以改变描述的语序，也可以通过画像改变实际风味与评分，但是评语不能凭空写入 8% ABV 或擅改总分。BJCP 五项分值由同一套评分器结算。与未增味底酒的对比固定种子、发酵操作、木桶、包装、储温、酒龄和申报类别，给出五项分差以及 FG、ABV 差值。

材料画像按规范化的原料名和处理方式复用。投料量、投放阶段、酒龄和风格是批次结算条件，不是原料身份。服务进程有定长的画像及请求缓存，并合并相同的在途请求。保存到当前批次的结果用于刷新和回看。离线版、无密钥、超时、模型拒答和无效结构均保留可玩的本地路径。

## 酒客

开门前按酒桶备留言。每桶最多存八张，每晚随机抽最多五张；原帖和跟帖同签，续杯和常客支线照常穿插。提前打烊时，已经播出的文字从库存扣除，没播的随原桶留到次日。酒桶撤下后，其余留言退出营业。刷新页面沿用已经保存的抽签结果和播放位置。

只在进场时补空位，使用当晚模拟产生的客人。每桶至多一批 `POST /api/guests`，给 Luna 的只有客人知道的酒牌、杯中印象、人物、口味和回复关系。正文用随手发给同桌的口吻。离线或请求失败时用已有的本地对白补足本次抽签。


## 运行与复现

Node 本地服务读取进程的 `OPENAI_API_KEY`。密钥只配置在运行服务的环境中。服务固定使用 `gpt-6-luna`、Responses API 的严格 JSON Schema 和 `store:false`。两个请求均没有联网搜索或生图工具。静态托管和单 HTML 文件可以运行离线玩法。单位测试使用可注入的模拟上游响应，可独立检查请求次数、缓存、白名单和失败回退。[模型文档](https://developers.openai.com/api/docs/models/gpt-6-luna) · [结构化输出](https://developers.openai.com/api/docs/guides/structured-outputs)

## 复算一组剂量

取美式淡色艾尔底方，基线版本 1、工艺版本 2，酿造种子取 24，使用本地拍碎生蒜画像。把一头蒜在这个例子里记作 45 g。50 L 加入 45 g 即 0.9 g/L，预期还能察觉原料气味，酵母速率处在零扰动档。10 L 加入 1,000 g 即 100 g/L，接种时加入会使计划开桶日有更多残糖、较低酒精度；若在熟成时才加入，先前的 FG 和 ABV 保持原值。本版对熟成添加结算风味，不另开一轮瓶内酒精再发酵。测试按这个相对关系验收，所有强弱阈值均为游戏标定。

## Sites 部署

`npm run build:site` 将原画、浏览器模块及模拟器放入 `dist/client`，将两个生成入口打包成 `dist/server/index.js`。Worker 从 Sites 服务端环境读取 `OPENAI_API_KEY`；静态文件通过平台 `ASSETS` 绑定提供。服务仅传出已经整理好的 JSON 上下文，密钥不会打入代码或浏览器模块。`/api/health` 只返回服务是否有密钥及模型名，不返回凭据。新站点默认仅自己可访问。

本地 Node 服务和 Sites 使用同一份 `createLuna`，缓存和字段校验保持一致。请求等待最多 90 秒，浏览器等待窗口略长；服务失败时仍使用本地结果。运行 `npm test` 可核验 Worker 的资源路由、来源检查、体积上限与无密钥降级。


线上发版时，部署完整的 Worker 与静态资源，并在 Worker 的 secret 中配置具有模型访问权限的 `OPENAI_API_KEY`。开门会等待留言请求，网关超时需覆盖服务端 90 秒的请求窗口。验收时用新桶或有库存空位的存档进入酒屋，在浏览器核对 `POST /api/guests` 返回 200、返回的留言出现在播放或剩余库存中，随后播放期间请求数应保持不变。提前打烊并带原桶进入次日，确认只补空位。`/api/health` 的 online 表示已配置密钥，模型可用性以实际留言请求为准。
